# Phase 6 hardening and rollout readiness

This is a review and future operator runbook, not deployment authorization. The tested base is `4aeb08039f1d31e0d2da90a351865363a34d67fa`; the rollback baseline is master-era `ef02de214bb6b6034d7dc3a7d14bdf3022b9219f`. All four flags below remain off. No production configuration, unit, service, session, or real message was touched in this phase. Use DeepSeek, never Codex, for production replies.

## Threat model and remaining risks

| Threat | Existing boundary / mitigation | Remaining risk and disposition |
|---|---|---|
| Instructions or malicious text in tool output | Explicit registered tools, closed schemas, current-message checks, separate tool role and instruction treating results as untrusted; no model-selected send or URL fetch; tool-assisted turns are not saved. Weather validates provider fields and returns a locally formatted response directly. Crisis uses fixed copy before tools. | The model can still obey injected text, echo it, or issue unsafe ordinary text; there is no general output safety filter. Instruction hierarchy is not a security sandbox. Keep new adapters disabled pending review; accept this residual only under an explicit operator decision. |
| Data exfiltration / query leakage | No search adapter or search provider exists. Weather accepts a city and qualifiers only when present in the current user message, with narrow character and length checks; geocoding receives the city and forecast receives coordinates, date, timezone and weather parameters. No conversation history or identity is deliberately sent to Open-Meteo. | Substring validation does not prove intent or informed consent; an accidental city-like substring can be shared. The user-facing disclosure is returned after the lookup, not prior consent. Provider sees IP and can log coordinates; [Open-Meteo](https://open-meteo.com/en/terms) says webserver logs are deleted after 90 days. DeepSeek receives the prompt/history and tool schemas as part of ordinary model processing. Confirm privacy and use terms before enabling; leave off if prior consent is required. Any future search needs separate design, explicit intent, minimization and provider approval. |
| SSRF / endpoint abuse | Weather endpoints are constants; input is validated and URL-encoded, redirects refused, response size bounded, and returned URLs never fetched. Health only accepts loopback HTTP origins with explicit ports and uses fixed paths, no redirects or proxy environment. | Weather's urllib opener can honor environment proxy configuration and DNS/TLS trust remains external; endpoint allowlisting is not an egress firewall. Limit egress/proxies operationally if required. The registry trusts adapter code and is not a sandbox. |
| Message or identifier leakage in logs/storage | Event logs contain metadata rather than message text or user ID; weather does not intentionally log URLs, responses or locations; health logs sanitized states. Tool-assisted turns are not written to short-term memory. Secrets are process environment only for the named protected keys. | Crisis JSONL alerts can contain user identifiers; short-term memory contains ordinary conversation; care choices/receipts are identity-linked and external. Unexpected exceptions are logged with tracebacks and third-party logging/proxies may record sensitive values. Protect logs, databases, backups and access; review retention and logging configuration. Do not claim logs are anonymous. OpenAI-compatible credentials are not in the protected `.env` denylist; keep them out of `.env` and avoid that provider in this rollout. |
| Resource exhaustion / cost | Registry executes at most 3 calls total across 2 tool rounds, serially, with a 10-second wait including semaphore acquisition and a 2,000-character encoded result cap; max 32 model-returned calls per round are parsed, with excess executions unavailable. Per-identity rates, ingress size cap, and bounded weather response/cache and provider budgets apply. Health probes have bounded size/time/backoff and never restart or replay. | Limits are process-local, reset on restart, and are not a cluster-wide or monthly budget. The single event consumer can block later events, including crises, during a slow ordinary turn. A timed-out `asyncio.to_thread` weather request may continue in its worker; concurrency 1 governs registry awaiters, not necessarily already-cancelled worker threads. Model responses and input token cost are not capped by the tool-result limit. Monitor spend/latency and keep flags off until capacity and risk are accepted. |

Other existing limitations: onboarding and special cases occur before crisis detection; unexpected judge exceptions outside `JudgeUnavailable` are not uniformly treated as suspected crisis. OneBot send outcomes can be ambiguous and are not retried; queue and deduplication are in memory. Health's readiness does not prove delivery or authentication, and the prior inspected systemd restart policy is fast and unlimited. No change here repairs these separately scoped issues.

## Bounds, latency and cost

The generic DeepSeek loop allows up to two tool rounds and a final synthesis request, at most three actual tool invocations **total**, a stricter bound than three per round. A model may return up to 32 call descriptors per round; calls after the third receive unavailable results without executing, and >32 fails to fallback. Each model request has a 20-second application deadline by default. Three sequential model requests plus three 10-second tool waits can add up to approximately 90 seconds before safety judge, configured reply delay, sending and overhead; this is an illustrative budget, not an end-to-end SLA. Weather returns its formatted result immediately on a weather call, without a synthesis request. Its usual uncached lookup makes two sequential provider requests; a forecast cache hit still makes one geocoding request. urllib's three-second socket timeout is not a total wall-clock guarantee. No live latency measurement or load test was performed.

Each model round resends accumulated prompt, history, schemas and prior tool messages and is billed on input and output tokens. The code does not enforce a model token/spend budget. Actual price depends on model, cache hits and current tariff; consult [DeepSeek pricing](https://api-docs.deepseek.com/quick_start/pricing/) and set a separately managed spend budget. The code requests `deepseek-chat`, whereas the current [DeepSeek API documentation](https://api-docs.deepseek.com/api/create-chat-completion/) lists different model names; compatibility, applicable pricing and access must be verified by the operator before rollout, without exposing private content. No real provider call was made here.

Open-Meteo's [terms](https://open-meteo.com/en/terms) state free use is non-commercial, with fewer than 600 calls/minute, 5,000/hour and 10,000/day, and CC BY 4.0 attribution. Its [pricing](https://open-meteo.com/en/pricing) lists 300,000/month and says monthly enforcement is not yet active. The local adapter caps requests at 300/minute, 2,000/hour and 5,000/day per process, not per shared IP, and does not enforce a monthly limit. Other applications and multiple processes share provider limits. Two requests are normally needed per uncached result. Eligibility, network reachability, provider terms, limits and costs must be reviewed again before enabling.

## Configuration and rollout gates

| YAML flag | Default | Effect and prerequisites |
|---|---|---|
| `read_only_tools.enabled` | `false` | Global registry switch. When false, no read-only tool schemas are exposed. |
| `read_only_tools.policies.weather_lookup.enabled` | `false` | Weather requires this **and** the global flag; current-message city check and limits still apply. Enable only after privacy, eligibility, attribution, quota and provider compatibility review. |
| `connection_health.enabled` | `false` | Starts read-only local probes and exposes readiness on application startup; it never controls a process or session. Verify local endpoint access; authenticated OneBot can show unconfirmed. |
| `proactive_care.enabled` | `false` | Gate, scheduler, app wiring and chat control commands are wired since P6, but nothing is sent while this is false. The consent store and command surface only exist when `proactive_care.store_path` is also set (an operator-owned path outside the repository); with a store assembled, the opt-in/pause/stop/forget commands work even while sending stays disabled. Do not enable proactive sending (trigger parameters are a separate, unauthorised stage). |

A code rollout with all flags off is distinct from enabling features. Enablement and any real-message canary require separate supervisor authorization; no automated canary or messaging is part of this runbook.

## Future deployment and companion-only restart

These are operator steps for a separately approved maintenance window, not commands executed in this phase:

1. Record the actual deployed revision, exact local configuration and effective unit definitions securely; confirm the working directory, launcher and dependency versions. Back up the current code, local config, short-term memory and external care store if present, using access-controlled storage; test backup readability. Preserve session files and do not print secrets or identities. Check whether the deployed revision is in fact `ef02de2`; if not, record its actual hash as the first rollback target as well.
2. Validate the approved release commit and `uv.lock` in an isolated staging copy; run `scripts/test.sh` and `uv run ruff check .`, with fake services only. Confirm the four flags are false and preserve all existing production configuration and secret provisioning. Check effective companion `ExecStart`, `ExecStop`, dependencies and restart behavior with read-only systemd inspection. If restart could invoke NapCat, relay, watchdog or session operations, stop and resolve this with the operator; do not proceed.
3. In the approved deployment checkout, install the reviewed release by the site's normal controlled mechanism, keeping the previous revision and config recoverable. Run `uv sync --locked` in that checkout, using the existing runtime environment and without changing the unit. Do not touch the NapCat unit, relay, QQ process, login or session state.
4. Only after explicit deployment approval and the dependency checks above, the operator may run `systemctl restart qqbot-companion.service` (with the site's normal privilege mechanism). Do not run `daemon-reload`, restart NapCat or invoke login. If the unit cannot be safely restarted independently, stop and escalate. This procedure has not been executed against the running service.
5. Check companion unit status and sanitized event/error counts, confirm the active revision and all flags, and inspect health only if separately enabled. An active unit or `/health/ready` does not prove the relay, login or end-to-end delivery. Use synthetic staging checks; any real QQ message needs separate authorization. Confirm no unexpected duplicate sends or alerts using metadata only. Record revision, flags, time, outcome and operator without message content or identifiers.

Stop rollout and roll back for startup failure, degraded reply or crisis path, leakage, unexpected sends, sustained latency or provider errors. If login is offline/unconfirmed, leave session state intact and escalate; do not attempt login or restart NapCat.

## Rollback

1. Disable enabled new flags in the secured deployment configuration and retain the exact pre-change version. If config cannot be applied without restart, continue with the approved companion-only restart below. No proactive sending is authorized.
2. Restore the actual previous known-good code and matching dependencies/config; the requested master-era baseline is `ef02de214bb6b6034d7dc3a7d14bdf3022b9219f`. Use a deployment checkout or approved release mechanism, not a reset of the development branches. Verify revision and dependencies before restarting. If the pre-deployment revision differs from the baseline, use its recorded revision/config first and escalate before a further downgrade.
3. Following the same unit-dependency checks, restart **only** `qqbot-companion.service` under separate authorization. Verify status and sanitized logs, and run the approved synthetic checks. Do not retry ambiguous sends, replay queued messages, or alter NapCat/QQ login and sessions.
4. No existing memory schema was migrated. Preserve the short-term database. If a separately deployed external care store exists, archive or remove it only under the operator's retention policy, including journals/backups; do not overwrite unrelated memory. If service or login health remains uncertain, stop and escalate.

The release and rollback must be rehearsed in an isolated copy; this does not prove the real host's launcher, dependencies, secrets or session health.
