# Connection health and recovery

This feature is disabled by default: `connection_health.enabled: false` in the application YAML. Enabling it starts one task inside companion's existing process. It reads two fixed systemd unit states and sends only local GET requests to companion `/health/ready` and OneBot `/get_status`. It has no process-control, login, QR, message, replay, DeepSeek, or session-management operation. A new HTTP client is opened and closed for every probe; only probes are repeated. No message delivery is retried, including a timeout whose outcome is ambiguous. An accepted event and its deduplication are in memory, so delivery is not exactly once.

The fixed ingress probe uses `http://127.0.0.1:8090`; the OneBot origin is `napcat_base_url` (default `http://127.0.0.1:3000`). Only loopback HTTP origins with an explicit port are accepted. Probes do not follow redirects or use proxy environment settings. They have a three-second total timeout and a 4096-byte response limit, and do not attach credentials. A deployment requiring OneBot API authorization will therefore report an unconfirmed state until an independently reviewed configuration is available. `/health/ready` reports only that the event consumer is running; it does not prove relay delivery, authentication, queue progress, or successful replies.

Transitions are logged only when the sanitized snapshot changes. `companion_process` and `napcat_process` are systemd unit `ActiveState` values; they do not independently prove the QQ child process is alive. The corresponding `Result` values include `start-limit-hit` where reported. `ingress` is `ready` or `unready`; `onebot` is `reachable`, `disconnected` (including timeout), or `not_probed` (unit stopped/failed). `qq` is `reported_online`, `offline`, or `unconfirmed`. A valid OneBot envelope with `data.online=true` and `data.good=true` gives `reported_online`; no separate authentication check is made. Any other condition yields `operator_action_needed`. If the unit is stopped or failed, OneBot is not probed; a reachable but offline or unconfirmed status is sampled at the ceiling interval without recovery escalation. Disconnections and ingress faults retry only the safe probes with exponential backoff starting at 5 seconds, 0.8–1.2 jitter and a 300-second ceiling. Fully healthy samples run every 30 seconds; the failure counter resets after 120 continuous seconds of healthy samples. No assumption is made that silent login can succeed.

[OneBot 11 get_status](https://github.com/botuniverse/onebot-11/blob/master/api/public.md#get_status-%E8%8E%B7%E5%8F%96%E8%BF%90%E8%A1%8C%E7%8A%B6%E6%80%81) defines `online` as QQ online state and `good` as overall health. The deployed NapCat bundle inspected for this work returns `online` from `selfInfo.online` and hard-codes `good=true`; consequently these signals do not establish current authentication independently and may miss a silent disconnect. No production API was called during this work.

## Inspected deployment baseline

Read-only inspection on 2026-10-30 found system units `qqbot-companion.service` and `qqbot-napcat.service` with no drop-ins, `Type=simple`, no explicit User or Group (system service default: root), `After=network.target`, `Restart=always`, `RestartSec=0.1`, `StartLimitIntervalSec=0` (start limiting disabled; burst value 5 is ineffective), and no systemd watchdog timeout. The companion unit executes `runtime-24h/companion-launch.py`; its configured stop timeout is 15 seconds. The NapCat unit executes `runtime-24h/napcat-watchdog.py` with `KillMode=process`. That existing deployment watchdog checks for a QQ process, occupied ports, and a lock, and can launch a child itself. The repository also contains a separate optional legacy watchdog that can invoke a start command. Neither watchdog is started or modified by this feature. Thus the existing deployment already has an additional process supervisor, and its fast, unlimited systemd restart policy can itself cause a restart storm; this change neither fixes nor worsens that pre-existing policy. Systemd remains the only process lifecycle owner added or used by this feature. A service's active status alone does not establish that the NapCat child or QQ is online.

No unit override is proposed or applied in this change. Any future override or change to the existing deployment watchdog requires separate review and isolated tests, including start-limit exhaustion and rollback; never restart NapCat in response to a network or DeepSeek outage. If the login is offline or cannot be confirmed, leave session state intact and ask an operator to investigate; do not attempt login or session manipulation automatically.

## Rollback

Set `connection_health.enabled: false` in the application configuration and apply that change only under a separately authorized deployment procedure; the task then will not start on the next normal application start. Revert this commit or return the code to the known-good base `4d69ddb7d2e9c4b7d21c1816299d8a0cf5997fca` using the approved deployment procedure. No data migration or session change is involved. Since no unit files are changed here, no unit rollback is necessary. If a separately approved future override is rolled back, restore the exact previously saved unit files and remove only that override, verify the effective settings match the baseline above, and perform any daemon reload or service action only with separate authorization. Preserve all QQ session state.
