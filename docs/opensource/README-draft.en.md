# Anian · companion-bot (Draft)

> "Anian" (companion-bot) is a safety-first QQ private-chat AI companion bot and lightweight framework built on NapCat / OneBot v11: all 167 canonical NapCat actions are registered and funnelled through a single tiered-authorisation gateway, crisis replies are never generated by a model, and delivery quotas, ledgers and three-state receipts are owned exclusively by an independent delivery service.

[![License](https://img.shields.io/badge/license-MIT-green)](#licence)

## Features

| Capability | Description | Default |
|---|---|---|
| Private companion chat | LLM-driven private companionship with pluggable personas (4 persona packs, with SHA-256 verification and a safety wrapper) | On (default persona) |
| Image understanding | Private-chat images / image+text are answered via a vision model (≤3 images per turn, ≤10 MiB per image); image fetch uses NapCat local mediation with a direct-fetch fallback, behind SSRF boundary checks | On |
| Multi-bubble replies | When explicitly asked for item-by-item output, replies are sent sentence-by-sentence (up to 10 bubbles), with outbound review and identity-disclosure checks | On |
| Read-only tools | Current time, weather, web search, anniversary countdown (each with a global switch plus a per-tool switch; anniversaries can be added, removed and listed by the owner in private chat and are visible to the owner only) | On |
| Group chat | Group-message observation and classification; group replies / group sending are separate dual switches | Per production config |
| Proactive care | Opt-in consent surface, ≤30-day expiry, night-time silence, double re-check before sending, fully fail-closed | **Off** (wired, not enabled) |
| Full NapCat surface | 191 actions individually registered and dispositioned; all 167 canonical actions integrated (see below) | Tier-gated |

## Architecture

Inbound messages pass through **11 named stages** in order (the order is the contract; reordering turns the tests red):

```
TransportGate → Normalize → Admission → SafetyJudge → InboundRateLimit
→ Command → MemoryLoad → Persona → Respond → OutputGuard → Deliver
```

Two services hold exclusive semantics (no bypass via plugins or the application layer):

- **ActionGateway**: the single funnel for every outbound NapCat action — subject validation → tier gate (L0–L3) → per-resource authorisation (irreversible actions require a one-time confirmation token) → idempotency ledger against replay → allowlisted-field audit (credentials never enter logs). Business code may only call it through 9 typed facades.
- **DeliveryService**: the sole bookkeeper for chat-delivery quotas and concurrency, with two quota layers (per-target + total account budget; crises use a separate critical channel). The ledger and conversation history are persisted in the same transaction, and receipts are three-state (accepted / rejected / ambiguous; ambiguous is never resent).

The framework targets an eight-layer architecture (apps / adapters / pipeline / domain / services / ports / infra / config); the pipeline layer is fully landed and the remaining layers are migrated in by contract, with current differences recorded honestly in `docs/architecture.md`.

### NapCat action registry

Reconciled three ways against the official bundle of the local NapCat 4.18.41; all **191** entries have a final disposition:

- **All 167 canonical actions integrated**: L0 read-only 61 / L1 routine 62 / L2 management 36 / L3 high-risk 8 (L3 is hard-disabled by default and can only be unlocked in a controlled way via an operator allowlist + restart)
- The remaining 24 entries each carry a written reason (internal-only 6 / unsupported 4 / ops-only 2 / deprecated 2 / pending verification 2 / aliases and non-existent entries, etc.)
- All 32 inbound event types covered (only private chats enter the companion pipeline; the group path only observes); 23 message-segment types registered, 21 sendable

## Safety design

- **Crisis handling is never model-generated**: dual detection via keywords + a model judge; any hit follows a fixed template (hotlines 12356 / 110 / 120); any judge anomaly is conservatively treated as a suspected crisis.
- **Safety judgement cannot be bypassed**: SafetyJudge sits before rate limiting at a fixed pipeline position; persona-pack text is always wrapped inside a fixed safety wrapper.
- **Tiers and authorisation**: L2 actions require per-resource authorisation; irreversible actions require one-time confirmation tokens; L3 is hard-disabled by default.
- **Privacy and log discipline**: logs and metrics record metadata only (result codes, summaries, byte counts) — never message bodies, image content, URLs or credentials; "forget" means real deletion.
- **Identity disclosure**: outbound replies pass an identity-disclosure check; the bot never impersonates a human.

## Quick start

Prerequisites: Python 3.12+, `uv`, a QQ account that can sign in by QR code, and a DeepSeek API key.

1. Clone this repository and run `uv sync` to install dependencies.
2. `cp config.example.yaml config.yaml`, and set `allowed_private_user_ids` to your own QQ number.
3. `cp .env.example .env` and fill in the non-secret items; supply the required secrets as process environment variables instead: `ONEBOT_SECRET` (a random string you choose) and `DEEPSEEK_API_KEY`; optional: `TAVILY_API_KEY` (web search). Secrets are only read from the process environment — values written into `.env` are ignored with a warning.
4. Start NapCat following the official NapCat instructions (locally or via Docker) and sign in with your QQ account by QR code.
5. In the NapCat WebUI, configure the OneBot integration: the HTTP API and event-report URL point at companion (default `http://127.0.0.1:8090/onebot/event`), the token matches the `ONEBOT_SECRET` from step 3, and the message format is array.
6. Start companion: `uv run uvicorn main:app --host 127.0.0.1 --port 8090`.
7. Verify by sending a private message from an allowlisted account; then send an image to verify the vision reply.

> For production deployment (systemd supervision, disconnect recovery, backup policy) see `docs/deployment-runbook.md`; that runbook contains environment-specific paths. A generalised installation guide is in `docs/opensource/INSTALL-draft.md` (draft).

- CI runs tests, ruff and a gitleaks scan on every push / PR.
