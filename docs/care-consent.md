# Consent and care boundary (Phase 5 slice, wired in P6)

The care surface is wired but dormant: `proactive_care.enabled: false` is the default and nothing is sent while it is false. P6 added the application wiring: chat control commands (opt-in / pause / stop) routed to `CarePreferences` from the Admission pre-branch, a `CareScheduler` whose queued work is sent only through `CareSendGate`, and scheduler lifecycle hosting in the app lifespan. The gate receives the same shared `DeliveryService` instance as ordinary replies (one quota ledger), a live whitelist callback (the configured care-known user list), and a current safety callback returning the current `SafetyGateway`, an explicit allow decision (false while a crisis response is pending for that user), and a revision that changes whenever the safety state changes. Missing, failing, or changing checks fail closed. The consent store and command surface are only assembled when `proactive_care.store_path` names an operator-owned path outside the repository; without it there are no care commands. Trigger cadence and volumes (the D2 parameters) are a separate, not-yet-authorized stage: wiring alone creates no schedule of sends, and changing the flag alone does not retroactively create queued work. A reminder is not a crisis response, emergency service, or a promise that anyone is being monitored. Existing fixed crisis replies keep their critical route.

`CarePreferences` accepts only explicit opt-in, an expiry no more than 30 days away, pause-until, stop (withdraw consent), and forget (delete the choice). There is no fact extraction, free-text preference, conversation content, vector storage, or reminder content in the store. Its SQLite file must be outside the repository and is created with owner-only file permissions. The caller is responsible for an appropriately private parent directory, backup, and access control. There is no migration of the existing short-term memory database. Expired choices and 48-hour delivery receipts are purged on store operations or by calling `prune` during maintenance; an idle store requires maintenance to physically remove expired rows. SQLite backups, journals and filesystem snapshots have their own retention requirements.

The gate checks the flag, a live whitelist, unexpired and unpaused consent, current safety policy and crisis precedence, fixed-copy safety detection, 23:00–08:00 Asia/Shanghai quiet hours, and a single attempt per local calendar day. The OneBot gateway applies its current normal send rate and enable/dry-run policy at delivery. A transaction reserves the day and opaque work ID before sending; even a rate-limited, failed, timed-out, or ambiguous attempt consumes that day and is not retried. Work expires after 24 hours. Stop and forget immediately remove consent; minimal identity-linked receipts are retained for up to 48 hours to enforce the cap and prevent duplicate delivery even after a fresh opt-in. They contain no message text. Since P6 the private-chat forget command covers both stores: in one serialized step it clears the conversation history/ledger, the repetition tracker, and the care choices, and invalidates that user's queued care work, before the confirmation reply is sent (the care store is a separate external SQLite, so the two stores cannot share one transaction; serialization is the agreed substitute).

Rollback before any future deployment: keep `proactive_care.enabled: false`, leave `proactive_care.store_path` unset (the care surface then does not exist), and return to the pre-P6 commit using the normal deployment procedure when authorized. The new store is separate from existing memory; archive or remove only that external store and its journals/backups according to the operator's data policy. Do not restore or overwrite the unrelated existing memory database. No service changes are performed by this implementation.
